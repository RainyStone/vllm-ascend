MoonEP 的负载均衡：收益是真的，但分母太小

把路由偏斜从 1.5:1 一路拉到 99:1，量 MoonEP（slot）相对 all-gather（ag）在 MoE GEMM 关键路径上省下多少，以及端到端缺口还差多少。

结论

  1. 收益是真的，而且随偏斜单调增长：GEMM 关键路径上省 3.9 → 73.4 → 122.3 → 126.8 ms（0.6 / 0.8 / 0.95 / 0.99），最高 −28.5%。端到端缺口同步收窄 169 ms，两把尺子互证。
  2. 但收益在 0.95 之后饱和：ag 的热卡被总行数封顶（437 → 445 ms 几乎不动），MoonEP 稳定在 ~318 ms。能省的极限就是 ~127 ms。
  3. 即使 99:1，MoonEP 仍输 244 ms，而且这就是渐近值。缺口 > 收益上限，靠加大偏斜永远追不平。
  4. MoonEP 的额外开销不随偏斜变化：同一个 profile 窗口里 planning_kernel 1.644 s + barrier_on_stream_kernel 1.221 s，是编排侧的固定成本。要翻盘只能砍这里，与偏斜无关。
  5. 两条腿的钱花在不同科目上（图四/五）：ag 主要付给集合通信（565 / 944 ms），MoonEP 主要付给自己的编排（508 / 587 ms）+ 跨卡栅栏（181 / 237 ms）。两者的通信/编排量级其实相当（都占该卡设备时间的 50–70%），差别在于 ag 的通信能与其它 kernel 重叠（设备时间和 1372 ms > 实测墙钟 1294 ms），而 MoonEP 的栅栏把一切串起来（设备时间和 1381 ms < 实测墙钟 1687 ms，有约 300 ms 的空隙）。
