1. moonep slot 腿开启的 ascend-moonep 优化项

分两类：默认开启（代码路径/默认值=1，无需 env）与 本次显式开启（矩阵 slot 腿起服命令前缀 ASCEND_MOONEP_PREFETCH_RELAXED=1 ASCEND_MOONEP_NO_RECONCILE=1 ASCEND_MOONEP_SKIP_DUP=1，外加编排器统一的 MOONEP_MIN_DISPATCH_TOKENS=16）。全部开关在所有 rank 一致生效。

ASCEND_MOONEP_PREFETCH_RELAXED=1显式开启ascend-moonep prefetch C++env 显式开启（本次矩阵 slot 腿）摘掉 prefetch 的两个跨卡 barrier（aclshmemx_barrier_all_on_stream）：源是 peer 的 home chunk、init 后不变，前后栅栏对本用途排不出有意义的序；kernel 内 MTE3_MTE2 事件已保证 GET 完成可见。同时为 side-stream 发射扫清时序障碍。用户指定的历史收益项；ascend-moonep e189239
ASCEND_MOONEP_NO_RECONCILE=1显式开启ascend-moonep apienv 显式开启（本次矩阵 slot 腿，与 RELAXED 成对）跳过每层 3 次（dispatch/prefetch/combine 后）的 host 侧 npu.synchronize + dist.barrier 对齐 shim——该 shim 曾造成 51~60% 设备空转，且让 host 永远跑不到设备前面。RELAXED 摘掉 prefetch 的 host barrier 后，剩余三个设备内联栅栏各 rank 同序同次、代际天然一致，无需 host 重排。ascend-moonep 4995a63（profiling 中对应明显设备空转）；成对前提见 api.py:595
ASCEND_MOONEP_SKIP_DUP=1显式开启ascend-moonep planning C++env 显式开启（本次矩阵 slot 腿）planning 短路 source-dup 阶段（counts→prefixes→payloads + 2 次 inbox 轮询）；代价是 dispatch 多传重复的 hidden 行（dispatch 本身才 ~180μs/层），换取 planning 大幅变快。journey 报告实测：dp0 长尾 1219.7→24.5μs；ascend-moonep c75a271

6. 综合结论

6.1 slot 对负载倾斜几乎不敏感，off 随倾斜线性变慢

TTFT 从均匀到最倾斜（峰均比 1.00→2.98）的变化幅度：

条件off 变化幅度slot 变化幅度

max_num_batched_tokens=16384 · 输入 8k token+42%+7%
max_num_batched_tokens=16384 · 输入 16k token+47%+1%

slot 的平线来自它的工作方式：热点专家的权重行被镜像到每个 rank 的槽位、提前预取，再由 planning 按真实 token 负载把计算行均摊到各 rank——最忙 rank 不再拖住整个波次。off 没有这层均衡，最忙 rank（s=2.98 时承担 74.6% 载荷）决定全体速度。

6.2 盈亏平衡点：峰均比 ≈ 1.7~1.8（max_num_batched_tokens=16384 时）

在 max_num_batched_tokens=16384（一步装下全部输入）时，off 随倾斜变慢的曲线与 slot 的平线相交于峰均比 ≈1.7~1.8（8k 与 16k 两种输入内插结果一致）。低于该值 off 更快（最多快 19%），高于该值 slot 反超（最多快 21%、吞吐高 31%）。max_num_batched_tokens=8192 且输入 16k 时，输入被切成两步、slot 每步的起步耗时付两次（机制见 §5），四档倾斜下 slot 全部落后。

场景建议
