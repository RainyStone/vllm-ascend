1. 背景:两条路线

① MC2 —— Ascend 原生融合路线(基线)

expert-parallel 的 token 交换由两个 aclnn 融合大算子完成: npu_moe_distribute_dispatch_v2 / combine_v2。 MC2 = Matmul-Communication ×2:dispatch/combine 与前后 GEMM 在算子内部流水, 通信等待被 cube 计算覆盖;底层是 HCCL(all2all)。对上层只暴露一次调用,没有 plan 表与跨层状态。

② MoonEP —— 对称内存单边路线(本研究)

token 行按「专家属主」经 CANN SHMEM 对称内存做单边搬运,替换 HCCL all2all。 与 MC2 最本质的区别:通信目标地址在 planning 阶段就完全确定(显式 plan 表), 因此收发双方不需要握手协议,搬运可以当作纯数据搬移来做——这也是后文判断"能否融进大算子"的关键。

2. 对称内存:是什么、里面装了什么

对称内存(SHMEM):每个 rank 在自己显存里申请一块缓冲,并把它的物理句柄 (Fabric V2 / shareable handle)注册给 SHMEM 运行时;运行时保证每张卡上这块缓冲的虚拟地址相同。 于是「rank r 的第 X 字节」可以用一个地址表达:aclshmem_ptr(base_va, pe=r), 任意卡都能直接读写,不需要对方参与 —— 这就是「单边(one-sided)」。 Ascend 上要求接收侧显式 aclrtMemSetAccess(我们在 DP 场景还修了它的逻辑/物理 device id 问题)。

4. planning 内部:它有通信吗?产出的表有什么用?

4.1 有,而且是跨 rank 协作核

planning 不是纯本地计算。核内节奏(函数名取自 kernels/planning.cpp):

  • 本地直方图:各 rank 先算自己的 per-expert 计数(向量 reduce,ReduceTpeRowsReg 系列);
  • 跨 rank 汇总:把计数/归属行发布到对端对称内存的 inbox(PublishSourceDupCounts / PublishSourceDupPrefixes),对端 WaitForSourceDupInbox 等待, owner 端做 reduce 得到全局每专家负载;
  • 完成同步:用 payload-done 旗标(PublishSourceDupPayloadDoneFlags / WaitForSourceDupPayloadDoneFlags,写对端 aclshmem_ptr(base, dest) 的既定偏移)对齐各 rank;
  • 生成输出:BuildSourceDupDestinationPrefixes → MaterializeSourceDupOutputs 落表;核尾一次全 rank 栅栏。

也就是说:planning 的通信量很小(计数/前缀 + 旗标,不是 token 数据),但同步面很宽——它必须在所有 rank 都到齐后才有全局视图。这决定了后面融合判断:planning 是「全局耦合」的阶段,而 dispatch/combine 是「点对点」的阶段。

6. prefetch 在哪个阶段

prefetch 不在默认(owner)路径上,只在 MOONEP_SLOT_MODE=1(冗余专家平衡模式)里出现,位置是 dispatch 之后、专家 GEMM 之前: token_dispatch → prefetch_projections(plan.experts_to_copy) → grouped GEMM → token_combine。

  • 搬什么:被选中的「远程专家」的权重行(w13/w2),从对端对称权重区 GET 到本卡的 B 个槽 chunk;
  • 为什么:这些专家的 token 就不必发到对端了 —— 行留在本地,用槽里的权重本地算;
  • 代价:每层一次权重搬运(几 MB)+ 本地多算这些行 + 槽显存;所以只有在路由倾斜严重时才划算 (本机 2 卡 E=128 均匀路由下不均衡仅 0.63%,开着反而亏)。

7. 什么是 Megas MoE(融合大算子)

把 MoE 一层里的多个阶段 —— token 交换(dispatch)、分组 GEMM、激活、加权归约(combine) —— 收进 同一个设备核,用核内栅栏 / 多流水(cube 与 vector、搬运与计算)把通信等待藏到计算后面。业界三条路线:

  • MC2(本机基线):dispatch/combine 与 GEMM 在算子内流水,是 Ascend 上现成的 mega-MoE 形态;通信底层绑定 HCCL。
  • fused-kernel 流派(DeepGEMM 风格):单核内完成分组 GEMM + 激活 + 归约,靠持久化线程块与流水隐藏搬运。
  • MoonEP 的对称内存流派:显式 plan + 单边 RMA,通信与计算目前是两个阶段(尚未流水)。

融合的本质收益是让通信与计算重叠,其次才是省 launch 与中间张量往返。

8. 重点:把 MoonEP 融进 Megas MoE —— 亲和还是冲突?

逐维度对照 MoonEP 的设计与「单核多阶段流水」的需求:

维度MoonEP 的做法对融合核的影响判定
寻址方式plan 表预先给出「第 i 行写到对端哪个偏移」 核内搬迁无需原子分配、无握手协议,可静态划分搬运任务到各 AIV/搬运队列 亲和
通信语义单边 PUT / GET(不需要对端参与) 可以与 cube 计算并行发起,不占用对方的执行资源;天然适合「搬运引擎 + 计算引擎」双流水 亲和
通信底层SHMEM 对称内存,无 HCCL 通信域/流依赖 自研融合核可以直接用;MC2 的融合算子却是 vendor 闭源、无法改造 亲和
数据布局shard 按专家分段落位,cu_seqlens 直接就是 group_list GEMM 的 tiling 与通信的目标布局一致,核内无需重排(gather/scatter 都可省) 亲和
去重表同 token 到同卡只搬一行,接收侧本地复制 网络量降到「不同目标卡数」;核内多一段本地复制,但搬运压力显著下降 亲和
零同步 host 路径已改成全设备侧推进(行计数不再回 host) 融合核要求 host 不进关键路径 —— 这一步已经做过,是融合的前置条件 亲和
planning 的跨 rank 栅栏全局汇总 + payload-done 旗标 + 核尾全 rank 栅栏 冲突:一个阶段的自旋等待会阻塞整个核的流水(核内没有别的活可干);planning 必须所有 rank 到齐才有全局视图 冲突
动态 shape每步 T、每层路由都不同,plan 表每层重算 融合核的循环边界变成数据驱动(读 plan 表),tiling 效率与寄存器/UB 预算都更难静态化 冲突
容量补齐(pad)补到步长容量,尾部行使零权重 融合后 pad 行使 GEMM 与 combine 都白跑一段(可用 real-T 路径缓解) 冲突
slot prefetch(权重搬运)GEMM 前必须等权重 GET 完成 会插入一次核内等待;本场景收益为负,融合时可先不做 冲突(可裁剪)

结论:MoonEP 的「显式 plan + 单边对称内存」与 Mega-MoE 是亲和的——静态寻址、单边 put/get、 无 HCCL 依赖,恰好是融合核需要的性质(MC2 的融合算子反而因为是 vendor 闭源而无法改造)。 唯一结构性冲突是 planning 的全局耦合,所以推荐「核外 planning + 核内 dispatch/GEMM/combine」的边界。 建议先做低成本的第一步(planning 保持独立、把 dispatch 与 GEMM1 合核验证重叠收益),再评估是否值得自写 GEMM。
