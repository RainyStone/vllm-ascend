# 切分场景性能退化机制分析：max_num_batched_tokens < 输入长度时的 MoonEP slot 路径

日期：2026-10-16 · 数据来源：op2 性能矩阵（bench）与 20261011_off_vs_slot_profile_3hot1r（算子 profiling）

---

## 1. 问题定义

MoonEP slot 模式下，当 `max_num_batched_tokens`（同时为 MoonEP dispatch 静态共享内存容量 S）
小于输入长度时，chunked prefill 将输入切分为 ⌈L/S⌉ 个调度步。观测现象：

- 输入 8192、S=8192（单步容纳）：峰均比 s ≥ 2.48 时 slot 相对 off 取得 4.5%~17.3% 的 TTFT 优势；
- 输入 16384、S=8192（切分为 2 步）：全部四档峰均比下 slot 均劣于 off（+10.3% ~ +50.6%）；
- 输入 16384、S=16384（单步容纳）：s ≥ 2.48 时优势恢复（−12.9% ~ −20.7%）。

本文定量回答：切分引入的额外耗时在算子级分布于何处、其产生机制是什么、以及为何抵消了
高倾斜下的收益。

## 2. 数据来源与统计口径

### 2.1 bench 数据（op2 矩阵）

- 配置：DSV4-Flash（FP8，E=256，K=6，43 个 MoE 层），DP=4/TP=1/EP，Ascend950PR 卡 0-3，
  仿真路由注入（uniform s=1.00 / 3hot1r s=2.48），vllm bench serve：32 prompts、并发 16、
  输出 1 token、request-rate=inf；每配置 3 轮，第 1 轮为热身剔除，统计取第 2/3 轮均值。
- 每步 TTFT 的定义：TTFT 均值 ÷ 每 rank 每轮 prefill 调度步数。步数由服务日志中仿真路由
  打印的每步 token 数（T=）直方图确认：S=8192/L=16384 为 16 步×T=8192；S=16384/L=16384
  为 8 步×T=16384；L=8192 为 8 步×T=8192。

### 2.2 profiling 数据

- 配置：卡组 4-7，3hot1r 路由，L=16384/输出 1，seed 21001（两腿相同），torch profiler，
  单轮 bench 期间 start_profile/stop_profile 采集，两腿采集窗口语义一致。
  两腿配置仅 BATCHED_TOKENS 不同（16384 vs 8192）。
- 分析基于 torch_npu analyse 产出的 kernel_details.csv / op_statistic.csv。
- **bench 窗口界定**：以持续时长 >2ms 的 `KvQuantSparseAttnSharedkv` 内核（仅出现于 prefill
  步）的首末时刻为窗口边界（尾侧放宽 50ms）。所得窗口：基准 22.0s、切分 30.1s（rank0）。
  该方法排除 warmup、DP 空转步与导出阶段。
- 等时间切片的逐步归属为近似（切分场景各步时长不等），单步内核计数存在波动，但窗口总量
  不受切片方式影响。

### 2.3 有效性说明

- profiler 开销两腿同开，比值类结论不受影响；绝对值不用于跨实验比较。
- 逐步序列取 rank0；4 rank 合计的量级对照见 §4.2，结论一致。
- SIM_ROUTE 使各步路由分布恒定，排除路由变化导致的 plan 复用失效干扰（该因素在真实负载
  下存在，只会进一步增大切分代价，不影响本文结论方向）。

## 3. 现象量化（bench 推导）

### 3.1 每步 TTFT 与线性性检验（op2，uniform 档，轮 2/3 均值）

| 配置 | 步构成 | TTFT 均值(ms) | 每步(ms) | 线性检验 |
|---|---|---:|---:|---|
| off · S=8192 · L=8192 | 8×8192 | 4,106.1 | 513.3 | 基准 |
| off · S=16384 · L=16384 | 8×16384 | 8,221.6 | 1,027.7 | 2×513.3=1,026.6，偏差 +0.1%（线性） |
| off · S=8192 · L=16384 | 16×8192 | 8,316.5 | 519.8 | 与 513.3 偏差 +1.3%（切分不引入代价） |
| slot · S=8192 · L=8192 | 8×8192 | 4,745.4 | 593.2 | 基准 |
| slot · S=16384 · L=16384 | 8×16384 | 9,551.5 | 1,193.9 | 2×593.2=1,186.4，偏差 +0.6%（线性） |
| slot · S=8192 · L=16384 | 16×8192 | 12,526.7 | 782.9 | **2×782.9/1,193.9 = +31.2%（超线性）** |

结论：步长增大时 slot 严格线性；唯独"被切分的 8192 步"相对"独立 8192 输入的步"每步增加
31.2%（190ms）。同一现象在 3hot1r 档为 +37.4%（824.0 vs 1,199.9 ms/步），在卡组 4-7 的
profiling 实验中为 +32.0%（826.2 vs 1,252.4 ms/步，TTFT 13,219 vs 10,019ms）——跨卡组、
跨路由方向与幅度一致，切分引入的 TTFT 增量为 +3.0~3.6s。

### 3.2 与收益上限的对比

同输入长度（16384）、不切分（S=16384）时，s=2.98 下 slot 相对 off 的 TTFT 优势为 2,508ms
（op2）。切分引入的代价（+3.0~3.6s）大于任意峰均比下的收益上限，故四档峰均比下 slot
均劣于 off；劣化幅度随峰均比增大而收窄（+50.6%→+10.3%），与"代价恒定、收益随倾斜增大"
的模型一致。

## 5. planning 耗时构成分解

### 5.1 计算量与等待的分离

planning 内核的固有计算时长（无跨卡等待时的快速体）为数百微秒量级（基准窗口内 645 次
调用快速体合计 141ms，均值 0.22ms/次；切分 988 次合计 23ms，均值 0.02ms/次）。以 2ms
为界分离长时尾：

| | 基准 | 切分 |
|---|---:|---:|
| 窗口内调用数 | 645 | 988 |
| 快速体合计 | 141ms | 23ms |
| 长时尾次数 × 均值 | 295 × 4.9ms | 603 × 11.3ms |
| 长时尾合计 | 1,456ms | 6,800ms |
| 每步等待（÷8 / ÷16） | 182ms | 425ms |

调用数核算：prefill 步的期望调用数为 43 层 × 8 步 = 344（基准）与 43 × 16 = 688（切分）；
实测 645/988，超出部分（两腿均约 300 次 ≈ 7 个步 × 43 层）来自窗口内与 prefill 交织的
decode/对齐步（各 prompt 完成 chunk2 后产生 1 token 的 decode 步，同样经由 MoonEP 路径）。
**planning 的全部增量来自长时尾（跨卡等待），计算部分合计不足 25ms。**

### 5.2 逐步等待序列（rank0，等时间切片）

- 基准（8 步）：54, 198, 199, 198, 198, 203, 203, 199 ms —— 近似常数，均值 182ms，
  标准差 47ms（含首步热身效应）。
- 切分（16 步）：0, 882, 121, 750, 215, 632, 331, 495, 460, 371, 574, 274, 668, 156,
  786, 71 ms —— 均值 425ms，极差 0~882ms，标准差 271ms。

基准的等待呈低方差常数特征；切分的等待呈高均值、高方差特征。

### 5.3 逐步 attention 时长（同切片）

- 基准：每步 297~344ms，近似常数（各步均为 16k query / 16k KV）；
- 切分：每步 55~258ms 交替（chunk1 为 8k query / 8k KV，chunk2 为 8k query / 16k KV，
  后者约为前者的 2~4 倍）。

## 6. 机制推导

### 6.1 planning 等待的语义

planning 内核包含跨 rank 栅栏（共享代际计数器）：某 rank 的该内核时长中超出其固有计算
的部分，等于**四 rank 中最晚到达者与本 rank 到达时刻之差**。因此 planning 长时尾直接
度量了各 rank 到达同一 MoE 集合点的时刻离散度。

### 6.2 基准场景（各 rank 步形状恒同）

S=16384 时每个 rank 的每个 prefill 步均为 16,384 token 的完整 prompt：attention、GEMM、
通信各分量在 rank 间逐层相同，到达离散度仅来自调度与 host 发射抖动，故每步等待收敛为
近似常数（182±47ms）。

### 6.3 切分场景（步成本交替 + rank 间相位差）

两个因素叠加：

1. **步成本交替**：同一 prompt 的 chunk1/chunk2 的 attention 时长比为 1:2~1:4（§5.3），
   即调度步成本呈周期性交替而非恒定；
2. **rank 间相位差**：各 rank 的请求队列独立推进——某 rank 完成 prompt 的 chunk2 后，
   调度器插入该 prompt 的 1-token decode 步，而其余 rank 仍在执行 chunk 步；DP 波次
   对齐机制以空转步填充，使得同一波次内各 rank 执行的内容（chunk1 / chunk2 / decode 混合 /
   空转）不必相同。

当 rank A 处于低成本步（chunk1 或 decode）而 rank B 处于高成本步（chunk2）时，二者到达
下一层 planning 栅栏的时刻差等于两步成本之差（数百毫秒量级），先到者在该内核内空转。
由于相位差随队列推进漂移，等待时长呈高方差（§5.2 切分列），均值升至 425ms/步。

### 6.4 数量核算的层级一致性

- planning 等待差（rank0，窗口内）：6,800 − 1,456 = **+5,344ms**；
- 主要算子总差：**+8,004ms**（planning 占 65%，dispatch/combine 占 18%，其中 dispatch/
  combine 的增量同样以等待为主——其数据搬运量与 token 总量成正比，增量来自每步一次的
  汇合次数翻倍）；
- 窗口时长差：**+8,100ms**（与算子总差闭合）；
- TTFT 均值差：**+3,200ms**（TTFT 为各请求完成时刻的均值，小于 makespan 口径的窗口差，
  方向与量级一致）。

### 6.5 备择假设排除

| 假设 | 检验 | 结论 |
|---|---|---|
| attention 计算量增加 | 窗口内总量 0.99×；理论算术量 0.75×（带宽约束下读取量不变） | 排除 |
| dispatch/combine 数据量增加 | 两窗口 token 总量相同，数据量相同；增量 1.38×/1.32× 与汇合次数×2 的量级相符 | 非主因 |
| planning 计算量增加 | 快速体合计 141→23ms（反而下降，与 T 减半一致） | 排除 |
| profiler 不对称 | 两腿同窗同 profiler；bench 干净数据（无 profiler）独立复现 +31~37% | 排除 |

### 6.6 off 腿为何线性

off 腿（MC2/all-to-all）不存在 MoonEP 式的每步跨 rank 栅栏汇合：其跨 rank 等待并入 HCCL
集合通信，由热点 rank 的计算进度主导（峰均比决定），且通信成本随数据量线性。切分仅将
同一数据量分为两次传输，总成本不变（§3.1 off 行：519.8 vs 513.3ms/步，偏差 1.3%）。

## 7. 结论

切分（max_num_batched_tokens < 输入长度）在 MoonEP slot 路径引入的退化 **不是数据量或
计算量的增加，而是每步一次的跨 rank 栅栏汇合次数随步数翻倍、且步成本交替与 rank 间
队列相位差将单次等待放大约 2.3 倍**（182→425ms/步），叠加后 planning 等待增量 +5.3s，
构成窗口增量（+8.1s）的主要部分。由于 slot 的收益（消除峰均比导致的 rank 等待）按 token
总量兑现、不随步数增长，恒定的切分代价（+3.0~3.6s TTFT）在任意峰均比下均超过收益上限
（s=2.98 时 2,508ms），故切分场景下 slot 于全部峰均比档位劣于 off。

## 8. 优化方向与收益上界

1. **同 prompt 跨 chunk 复用 plan**：SIM_ROUTE（恒定路由分布）下两 chunk 的 plan 输出
   完全一致，可直接复用，消除一半 planning 栅栏汇合；真实 router 下路由分布随 token
   变化，需评估增量重规划或按 chunk 相似度条件复用。
2. **栅栏等待与计算重叠**：planning 发射提前（after_planning_hook 已具备挂点）或将
   dispatch/combine 与 attention 在流间重叠，可将等待隐藏于计算；收益上界为窗口差的
   65%（planning 等待部分）。
3. **降低 rank 间相位差**：调度器侧使各 rank 的 chunk 相位对齐（同波次内各 rank 执行
   同类步），可将等待恢复至基准的低方差常数水平。

## 补充（2026-10-16）：三场景 planning 等待逐步对照

新增场景 A（S=8192 · 输入 8192，独立 8k，off+slot 均已采集）后，可用同一窗口锚定方法
对三场景做逐步对照（rank0，bench 窗口内，等待=planning 内核 >2ms 部分逐步合计）：

| 场景 | 步构成 | attention 每步(ms) | planning 等待每步(ms) | 均值 | 标准差 | 极差 |
|---|---|---|---|---:|---:|---|
| A 独立 8k | 8×T=8192 | 175~201（恒定） | 52,129,127,126,22,126,66,0 | 81 | 49 | 0~129 |
| B 16k 整步 | 8×T=16384 | 297~344（恒定） | 54,198,199,198,198,203,203,199 | 181 | 48 | 54~203 |
| C 16k 切分 | 16×T=8192 | 55~258（交替） | 0,882,121,750,215,632,…,786,71 | 424 | 265 | 0~882 |

按每 16384 token 归一的总等待：A 162ms ≈ B 182ms ≪ C 850ms。

**判定性对照**：A 与 C 的调度步形状完全相同（T=8192），仅上下文不同（独立 prompt 的完整
输入 vs 16k prompt 的分块）。A 的等待呈低方差（标准差 49ms），C 为高方差（265ms）且均值
5.2 倍——证明退化不取决于步长或 token 数，而取决于分块上下文引入的两个条件：步成本交替
（attention 55↔258ms）与 rank 间队列相位差。A/B 的恒定 attention 与低方差等待共同构成
"同构步=同步推进"的对照组。

## 补充（2026-10-16 二）：等待发生于低成本步、等待时长=对端并发高成本步的层时长

逐步切片的 attention 计算量与 planning 等待呈反相关（rank0，场景 C）：
attn 258/55/215/83/195/113/164/143… 对应 wait 0/882/121/750/215/632/331/495…
（attn 71→wait 786，attn 92→wait 668，attn 231→wait 71，完全反向）。

算术闭合：高成本（chunk2）步的层时长 ≈ 900ms/43 ≈ 19~21ms；低成本步（chunk1 或 decode/
空转步）自身层耗时趋近于零，其在 43 个栅栏处各等待对端一个层时长：43 × 17~20ms ≈
730~860ms，与实测离群等待（750/786/882ms）一致。调用数分解：窗口内 planning 调用 988 ≈
(16 个 chunk 步 + 7 个 decode/空转步) × 43 层——低成本步（约 7 个）承载了等待的主体。

结论细化：切分场景的等待增量主要发生于**自身计算量接近零的步**（decode/空转步或低成本
chunk1 步）——这些步仍须经过全部 43 个跨 rank 栅栏，而对端 rank 正在执行高成本 chunk2 步，
故每个栅栏各等待约一个对端层时长。场景 A/B 中各 rank 同构推进，不存在此错位。

## 补充（2026-10-16 三）：decode 步不参与栅栏；相位错位的直接测量与 B/C 差异成因

修正与新增：
1. **decode/空转步（T=1 < MOONEP_MIN_DISPATCH_TOKENS=16）走 MC2 路径，不进入 MoonEP
   planning 栅栏**——其存在不产生 MoonEP 等待（两场景相同）。此前将高等待归因于 decode 步
   有误：高等待步的自身 attention 为 55~113ms，属 chunk1 量级（decode 接近 0）；窗口内
   planning 调用 988≈23×43，远小于"T=1 步也进栅栏"的预期。
2. **跨 rank 相位直接测量**（各 rank attention 时间序列按 100ms 桶对齐）：C 的错位时间占
   31%、跨 rank 相关系数 −0.53；B 为 11%、−0.12。
3. **B/C 差异成因**：参与栅栏的步的成本结构不同。B 单一成本档（16384 步），任意重叠都是
   等成本重叠，等待恒为抖动底噪（181±48ms/步）；等长步+栅栏锁定使节拍自同步、无失配点。
   C 两档成本（chunk1/chunk2 每层 1:2~4），chunk 交替边界构成周期性失配点，且失配代价
   不对称（便宜步方全额等待、贵步方零代价），错相持续再生而不自愈。
