1. 背景:两条路线

① MC2 —— Ascend 原生融合路线(基线)

MoE 的 expert-parallel token 交换由两个 aclnn 融合大算子完成: torch_npu.npu_moe_distribute_dispatch_v2 与 torch_npu.npu_moe_distribute_combine_v2。名字里的 MC2 = Matmul-Communication ×2:dispatch/combine 与前后 GEMM 在算子内部 流水,通信等待被 cube 计算覆盖;底层通信用 HCCL(all2all)。对上层只暴露 「一次调用」,没有 plan 表、没有跨层状态。

实测(本机 dp2ep2):decode 每层 dispatch 0.093 ms + combine 0.064 ms = 0.157 ms; 总吞吐 7719 tok/s(基线 1.00)。它在 2 卡、E=128、均匀路由下已接近最优。

② MoonEP —— 对称内存单边路线(本研究)

token 行按「专家属主」经 CANN SHMEM 对称内存做单边 RMA,替换 HCCL 的 all2all: planning 核算出「谁发给谁」的 plan,dispatch 核把行写进各 rank 的对称 chunk, combine 核把对端算好的行取回并按 K 求和。两个引擎变体: MTE(MOONEP_DISABLE_UDMA=1,走 MTE 搬运)与 URMA(带 URMA 上下文,走 UDMA 快路径)。对上层是三个独立核 + plan 状态, 因此 host 侧与同步开销天然比 MC2 高——这正是本报告后半段要分析的部分。

3. 什么是 Megas MoE(融合大算子)

「Megas MoE / Mega MoE kernel」指把 MoE 一层里的多个阶段——token 交换(dispatch)、 分组 GEMM、激活、加权归约(combine)——塞进同一个设备核,用核内 grid sync / 多流水(cube 与 vector、搬运与计算)把通信等待藏在计算后面。 业界三条已知路线:

  • MC2(本机基线):dispatch/combine 与 GEMM 在算子内流水,是 Ascend 上最接近 「mega MoE」的现成实现;缺点是通信底层绑定 HCCL(all2all),通信域随 EP 规模变贵。
  • MoE 的 fused-kernel 流派(如 DeepSeek 系、DeepGEMM 风格):单核内完成 分组 GEMM + 激活 + 归约,靠持久化线程块与流水隐藏搬运。
  • MoonEP 的对称内存流派:把「谁发给谁」显式化(plan),通信走单边 RMA, 天然适合跨节点与大规模 EP——但目前通信与计算是两个阶段,没有流水。

共同点:融合的本质收益不是「少写代码」,而是让通信与计算重叠,其次才是省 kernel launch 与中间张量往返。

4. 三档融合分析

第一档:planning + dispatch 合核 ✅ 建议做

做法AscendC 内两阶段 + 一次 SyncAll(仓内已有跨 rank 栅栏原语);plan 表只在本卡 device 内被消费,合核后省一次 launch、一次全 rank 栅栏与中间状态往返。
收益每层省 0.05~0.08 ms(launch ~17-20 µs + 栅栏 + plan 表读写)⇒ decode 约 +3~5%;prefill 的 planning 核 0.26 ms 是设备时间,只能省它的 launch 部分。
风险低-中:不碰 GEMM、不改数据布局、不动权重。

第二档:dispatch + gmm1 融合(MC2 式通信+计算融合)⚠️ 产品级决策

做法在核内实现「收行 → 立即参与分组 GEMM」的 cube/vector 流水 + RMA 流水,把通信等待藏进计算——即重写一遍 MoE 前向。
收益理论最大:吃掉当前 decode 差距(0.82× vs MC2)的大部分。
风险高:等于重新实现 vendor 已有的 MC2 融合算子,而 MC2 走 HCCL。MoonEP 做这一档的唯一理由是把它建在 shmem/RDMA 上(大 R、跨节点、HCCL 通信域成本高的场景)。

第三档:gmm1 + swiglu + gmm2 三合一

做法vllm-ascend 已有 grouped_matmul_swiglu_quant 这类融合(量化路径),bf16 下需新写或换用融合算子。
收益省 2 次 launch + 激活中间张量的读写 ⇒ 约 +2~4%。
风险高:GMM 最吃性能,手写 tiling 很可能打不过现成库。

收益上限与建议路径

  • 上限:decode 每层 0.202 ms 通信段里,launch/同步/边界拷贝约占 0.1 ms ⇒ 全部融合的理论上限约 decode +10~15%(把当前 18% 差距的 2/3 吃回来)。
  • 但大头是通信等待的隐藏,只有第二档(自写 GEMM)能吃 —— 那是「要不要把 MoonEP 做成产品级内核」的取舍,不是纯优化。
  • 路径:① 先做第一档(低成本、可量化、不碰 GEMM);② 第二档先回答目标场景是否为大 R / 跨节点——若只是 2 卡 E=128,本机数据表明 MC2 已接近最优,MoonEP 的结构优势发挥不出来;③ 第三档交给 GMM/算子团队或用 vendor 融合算子。
