# prefetch 会不会成为瓶颈?—— 以 DeepSeek V4-Flash 为对象的带宽与方案分析

**日期** 2026-09-28 · **目标模型** DeepSeek V4-Flash(E=256, H=4096, 43 层, top-6)
**对照模型** Qwen3-30B-A3B(E=128, H=2048, 48 层, top-8,当前实测基线)

> 本文的**几何数字全部实测自 config.json**;**链路带宽实测**自 8 卡 put 探针;
> 其余为推算,已逐条标注。**没有跑过 V4-Flash 的 MoonEP 实测** —— 这是本文最大的局限,§6 给出验证实验。

---

## 0. 结论

| 问题 | 答案 |
|---|---|
| prefetch 会不会成为瓶颈? | **会。** 在 Qwen3 上它离瓶颈三个数量级,在 V4-Flash 上会真实撞上 |
| 是带宽不够吗? | **不是 —— 第一道墙是 HBM,第三道墙才是真正致命的** |
| 真正的瓶颈是什么? | **"每专家行数太少 → top-B 槽位选择不稳定 → 每层翻转" × "单专家 50 MB"** |
| 三个方案里哪个值得做? | **只有 C(预测 + 与 attention 重叠)能治本。** A 治不了选择问题,B 的显存代价在新几何下更大 |

## 1. 换模型后什么变了

| | Qwen3-30B-A3B | **DeepSeek V4-Flash** | 倍数 |
|---|---:|---:|---:|
| hidden | 2048 | **4096** | 2× |
| moe_intermediate | 768 | **2048** | 2.7× |
| 专家数 E | 128 | **256** | 2× |
| top_k | 8 | **6** | 0.75× |
| 层数 | 48 | **43** | — |
| **单专家权重** | 9.44 MB | **50.33 MB** | **5.3×** |
| **全部 MoE 权重** | 15.5 GB | **554 GB** | **36×** |
| 激活参数(专家部分) | 31 GB→ 每 token 约 2.4 B | 约 6.5 B | — |

> 单专家 = `w13 (h×2·mi) + w2 (mi×h)`,bf16:
> V4-Flash = 4096×4096×2 + 2048×4096×2 = 33.55 + 16.78 = **50.33 MB**

**⇒ 三个量同时变大:专家更多(槽位集合更大)、每个专家更大(每次搬运更贵)、每专家行数更少(选择更不稳定)。**

---

## 2. 第一道墙:HBM(不是带宽)

```
全部 MoE 权重 = 256 专家 × 50.33 MB × 43 层 = 554 GB
单卡 HBM = 86 GB(实测)
```

| R | 每卡专家权重 | 预取槽位 | 合计 | 判定(留 25% 给 KV/激活) |
|---:|---:|---:|---:|---|
| 2 | 277.0 GB | 6.44 GB | 283.5 GB | ✗ 装不下 |
| 4 | 138.5 GB | 3.22 GB | 141.7 GB | ✗ 装不下 |
| **8** | **69.3 GB** | **1.61 GB** | **70.9 GB** | ⚠ **勉强**(只剩 ~15 GB 给 KV+激活) |
| 16 | 34.6 GB | 0.81 GB | 35.4 GB | ✓ 可行 |
| 32 | 17.3 GB | 0.40 GB | 17.7 GB | ✓ 可行 |

**⇒ 这台机器只有 8 张卡,所以 V4-Flash 的最优配置被卡死在 R=8,而且非常勉强。**

**这个约束比带宽紧得多,而且它顺带决定了后面所有数字** —— R=8 意味着:

- **B = E/R = 32 槽**(不是 Qwen3 的 64)
- **必须跨 2 个 UB 簇**(4 卡一个簇),链路是 UB + PCIe 混合

> ⚠️ **这个 HBM 账应该先和模型侧确认 R=8 到底跑不跑得起来。**
> 如果跑不起来,后面三节都是纸上谈兵。

## 3. 第二道墙:带宽

**全量重取** = 把 B 个槽位全部换一遍的字节量。

| | B | 全量重取字节 | 可用链路 | **耗时** |
|---|---:|---:|---:|---:|
| Qwen3 R=4 | 32 | 302 MB | 135 GB/s | 2.2 ms |
| **V4-Flash R=8** | **32** | **1.61 GB** | ~142 GB/s(3 UB + 4 跨簇) | **~11 ms** |

**对照:同样的 R=8 配置下,专家 GEMM 本身要多久?**

```
每 rank 行数 = T/rank × K = 2048 × 6 = 12288 行     (T=16384, R=8)
每行 FLOPs  = 2 × (4096×4096 + 2048×4096) = 50.3 MFLOPs
GEMM 合计   = 12288 × 50.3 M = 618 GFLOPs
按 300~800 TFLOPS/卡(bf16,假设值) → 0.8 ~ 2.1 ms
```

**⇒ 一次全量重取 ≈ 5~14 倍的专家 GEMM 时间。**

**这就是"prefetch 会不会成为瓶颈"的直接答案:会,而且量级上它比它服务的计算还贵。**

> 但这是**最坏情况**。今天的实测(Qwen3)显示实际只搬了全量的 0.8% —— 因为槽位持久、
> 路由稳定时什么都不用搬。**所以关键问题变成:V4-Flash 上槽位会churn 多少?**

---

## 4. 第三道墙(真正的瓶颈):每专家行数太少

**预取的算术强度** = 每专家分到的行数 × 每行 FLOPs ÷ 每专家字节

| 模型 | 行/专家 | FLOP/行 | MB/专家 | **FLOP/byte** |
|---|---:|---:|---:|---:|
| Qwen3-30B-A3B | 1024 | 9.4 M | 9.44 | **1024** |
| **DeepSeek V4-Flash** | **384** | **50.3 M** | **50.33** | **384** |

**⇒ V4-Flash 的预取性价比只有 Qwen3 的 1/2.7。**

**但这还不是最要命的。真正的问题是"选择稳定性":**

```
行/专家 = T × K / E

  T/rank    Qwen3(128专家)   V4-Flash(256专家)
   16384          1024              384
    8192           512              192
    4096           256               96
    1024            64               24     ← 开始不稳
     256            16                6     ← 小整数计数
      64             4              1.5     ← decode 量级
```

**槽位选择 = "按全局需求量取 top-B 个远端专家"。当行/专家只有个位数时:**

1. **计数是小整数,层间抖动大** → top-B 集合每层都在换
2. **每换一个专家就是 50.33 MB 搬运**
3. **一旦进入这个区间,prefetch 从"几乎免费"变成"每层搬几百 MB 到 GB 级"**

**★ 而 V4-Flash 在 T=16384 时就已经只有 384 行/专家,是 Qwen3 的 38%;
在 decode(T/rank 小)时直接掉进个位数 —— 那正是服务的主战场。**

**⇒ 结论:prefetch 的瓶颈不是带宽,是"选择不稳定 × 单专家过大"。加大带宽治不了,
加大 B 也治不了(反而更贵)。**

## 5. 三个方案的重新评价

### 方案 A:与 dispatch 并行

| | |
|---|---|
| 优点 | 已实现、语义干净、改动小 |
| 在 Qwen3 上的收益上限 | **104 μs/层 ≈ 5 ms/步** —— 太小,实测无墙钟收益 |
| **在 V4-Flash 上** | 上限仍是"prefetch 的暴露时间",但暴露时间从 104 μs 变成可能 **几 ms** ⇒ **收益上限变大** |
| 缺点 | **治不了选择不稳定** —— 它只是把等待藏起来,不减少搬运量。churn 高时链路被持续占用,"并行"退化成"争抢" |

**⇒ 在 V4-Flash 上有一定价值(藏掉暴露时间),但不是解法。**

### 方案 B:每层都缓存

| | |
|---|---|
| 优点 | 直接减少重取 —— **正好针对 §4 的 churn 问题** |
| **显存代价** | `层数 × 槽数 × 单专家` = 43 × 32 × 50.33 MB = **69.3 GB**(R=8) |
| **致命点** | 而 R=8 时每卡只剩 ~15 GB 给 KV+激活 —— **缓存要 69 GB,根本放不下** |
| 在 Qwen3 上 | 14.5 GB,也远大于它能省下的 <104 μs |

**⇒ 显存代价在新几何下把这条路彻底堵死。**

### 方案 C:提前预测 + 与 attention 重叠

| | |
|---|---|
| 核心优势 | **attention 是本地计算,完全不占链路**;16k 时 8 ms、32k 时 28 ms 的窗口 |
| **在 V4-Flash 上** | 全量重取 ~11 ms ⇒ **32k 的 28 ms 窗口塞得下**,16k 的 8 ms 塞不下 |
| **真正的价值** | **把约束从"必须把槽位选对"换成"预测得差不多就行"** —— 提前一层知道要什么,就有时间慢慢搬,不必每层赌 top-B |
| 缺点 | 预测错了浪费带宽且要走修补路径;需要保存一层历史 |

**⇒ 只有 C 针对的是根因。** A 藏时间、B 加缓存,都改变不了"top-B 在层间翻转"这件事;
C 通过**提前一层**把"当层必须命中"降级成"提前准备",给了纠错的时间窗。

**额外好处:窗口不占链路 ⇒ 可以顺手加大 B。** 在 V4-Flash 上这意味着能容纳更宽的远端专家集合,
直接缓解 §4 的选择压力。

## 6. 验证清单(按代价排序)

**① 先确认 R=8 跑不跑得起来(最便宜,决定后面有没有意义)**

```
每卡专家权重 69.3 GB + 槽位 1.61 GB,单卡 86 GB
→ 实际加载一次,看 KV 池能给多大
```

**② 实测 V4-Flash 的槽位变更率(决定 §4 是不是真的)**

```
跑一轮真实流量,统计相邻两层 experts_to_copy 的集合差异
若 churn > 10%,则每层多搬 ≥161 MB(R=8)→ prefetch 必然成为瓶颈
```

**③ 量 Qwen3 上 dispatch 的真实跨卡占比(上一版报告遗留的推断)**

```
slot 模式下 token 行应留在本地,跨卡流量以 prefetch 为主。
若 dispatch 也大量跨卡,方案 A 的"并行"会变成"争抢",需要重新评估。
```

**④ 只有 ①②③ 都支持,才值得做方案 C。**

---

## 7. 一句话

**在 Qwen3 上,prefetch 离带宽瓶颈三个数量级,不值一提;换成 V4-Flash,它同时被三件事推向瓶颈 ——
专家数翻倍(槽位集合更大)、单专家 5.3×(每次搬运更贵)、每专家行数降到 38%(选择在层间翻转)。
前两件是显存和带宽的量变,第三件是质变:它让"缓存 top-B 专家"这个模型本身失效。
三个方案里只有 C(提前预测 + 与 attention 重叠)针对的是第三件。**
