③ 结论

  1. TTFT 随 T 单调恶化。 T 从 69 涨到 4416（64×），slot/all-gather 比值从 1.09 涨到 2.47。方向明确：T 越小 MoonEP 越接近打平，但即便在 T=69 （≈ decode 的 64）它仍然慢 8.9%，没有反超。
  2. 跨卡不均衡与 T 无关。 四档全是 1.009–1.011，缩小 T 完全没有放大 不均衡 —— 这条假设被实验否掉。原因：T=69、K=8 时每卡每层只有 552 条 route 摊到 128 个专家，泊松噪声本身只有 ±4%，而 GSM8K 题目高度同质，实测偏差比随机还小。 ⇒ 这套负载上不存在可供 MoonEP 均衡的对象。
  3. 两条路线都是"两趟、等量字节"的跨卡搬运，差别不在搬多少，而在效率：
路线进 MoE 前出 MoE 后每卡跨卡字节量耗时随 T 涨 64× 的倍数
all-gatherall_gatherreduce_scatter 2(R−1)·T·H = 14 T·H8.7×（次线性）
MoonEP slotdispatch（MTE put）combine（MTE get + K-sum） 2·T·K·(R−1)/R·H = 14 T·H19.7×（接近线性）

（R=8、K=8：每个 token 的 K 条 route 里平均 7/8 跨卡 ⇒ 每趟 ≈7·T·H。 字节量相等，所以差异只能来自搬运的形状与实现层级：all-gather/reduce-scatter 搬的是 连续大块（HCCL 深度优化，实测每层切成 ~67 个大分片），而 MoonEP 搬的是 按专家分组的行级 scatter，包小、每次启动开销摊不开 —— 这正对应"线性 vs 次线性"。）

T=69 时那 8.9%（6.2 ms）的来源：MoonEP 每层多付 planning（跨卡直方图交换 + 1 次全局栅栏）+ 4 次 barrier_on_stream，约 129 µs/层 × 48 层； 而 all-gather 只有一次小搬运。

判定与下一步

  1. 在这类负载（GSM8K、8 卡 EP8、单请求/卡）上 MoonEP 赢不了：可均衡的对象不存在 （不均衡仅 1%），而单位 token 的搬运效率更低。
  2. 要救的方向是让 dispatch/combine 搬"大块"：例如先按目标 rank 做一次连续化重排， 再整块 put/get，而不是逐 (token, expert) 行发小包。这是库侧 kernel 改造。
  3. 待查的矛盾：早前文档记录的 MC2 decode 跨卡不均衡是 p50 1.20 / p90 1.50 / max 3.0， 而本次 slot 在 T=69 只有 1.01 —— 相差 20 倍，口径可能根本不同。这个矛盾决定了 MoonEP 到底有没有适用场景，应先查清再决定投入。

④ 为什么 MoonEP 是"线性"：dispatch/combine 的搬运粒度

现状：每条 route 一次 put，每次搬一整行 H。 外层循环遍历的是 route （token_id = i/K, topk_id = i%K），内层每条 route 发一次：

uint64_t hidden_off_bytes = loff * H * sizeof(HiddenT);   // 对方对称内存里该 route 的槽
aclshmemx_mte_put_nbi(
    hidden_symmetric + hidden_off_bytes,   // 目标 VA（aclshmem_ptr 拿到的对端地址）
    hidden_sh + token_id * H,              // 源：本地该 token 的 hidden 行
    row_elements,                          // = H 个元素（Qwen3: 2048 bf16 = 4 KB）
    dest_rank, event_id);
一次搬多少每层每卡次数每步（48 层）
MoonEP dispatch4 KB（1 行）T×K（T=4416 → 35,328）~170 万次
all-gather数 MB（连续大块）~67~3,200 次

⇒ 报文数差约 500 倍。这就是 all-gather 次线性（T 涨 64×、耗时涨 8.7×） 而 MoonEP 接近线性（19.7×）的根源：同样的字节量，一个走大块、一个走小包。

为什么必须是小包？ 因为发往同一个 dest 的行在源端 hidden_sh 里是 散落的（hidden 按 token 顺序排，而每个 token 的 K 条 route 各去不同的 rank）。

大块化方案（三步）

① 源端：扫一遍 topk_idx，按 dest 分组，把散落的行连续化到 staging buffer
   —— 一次卡内 DMA（读 T×H + 写 T×H，本地带宽，便宜）
② 网络：每个 dest 一次 mte_put_nbi，搬 [n_rows × H] 的连续块
   —— put 次数 T×K → R−1 = 7 次/层/卡   ★ 500× 的降幅
③ 接收端：目标布局当前是「专家连续」（GEMM 的 group_list 要求），而大块 put
   要求「来源连续」⇒ 接收端补一次 permute 成 expert-grouped

第 ③ 步不是新发明 —— 这正是 all-gather 路线里 aclnnMoeInitRoutingV3 干的事（实测 265 ms），也是 MC2/DeepEP 的标准 dispatch 结构。 做完之后接收端数据形态与 all-gather 路线一致，两条路线可共用同一套 MLP 接口。

报文数/层/卡需要源端重排
逐行（现状）T×K = 35,328❌ 就地发

语义澄清：这仍然是 one-sided

"one-sided" 的定义是通信的完成不需要对端执行配对操作。 源端 compact 是发送方自己设备内的数据重排，根本不涉及通信； 发送方本来就必须参与（是它发起的那个 put）。

步骤谁参与是否 one-sided
① 源端 compact本地 AIV不涉及通信
② 大块 put本地 AIV → 对端内存是
③ 接收端 permute对端本地 AIV不涉及通信

全程没有对面 CPU 参与：数据靠 aclshmemx_mte_put/get_nbi 直接落到对端 对称内存；完成通知靠 (a) 发送方把 flag 也 one-sided 写进对端、接收方设备侧轮询，或 (b) 设备侧栅栏（aclshmemx_barrier_all_vec，各 rank 的 AIV 进栅栏，不是 CPU）。 对比 HCCL：它也是设备侧，但用 AICPU kernel 做 rank 间协调，且是集合式（所有 rank 必须一起调用）。

4 次全局栅栏：时机与性质

profiler 实测 barrier_on_stream_kernel 4 次/层。来源不是"2 次 prefetch 调用"， 而是一次 prefetch_projections 调用里的 2 个投影（w13 / w2）各发一个 kernel （api.py:734 的 for full_weight in weight_prefetch_args 循环）， 而每个 kernel 前后各有 1 个栅栏（csrc/ops/prefetch.cpp:118 与 :134） ⇒ 2 投影 × 2 栅栏 = 4 次/层。

位置本意数据上必需？
进 prefetch 前"别在别人还在用 slot 时覆盖它"否
出 prefetch 后"别在权重还没到时就做 GEMM"否

库作者自己就说它们不必要（prefetch.cpp 里 RELAXED 开关的注释原话）：

  • 源是 peer 的 home chunk（init 时写好、之后再也不改）⇒ pre-barrier 无物可排；
  • kernel 自己的 MTE3_MTE2 event 已保证每次 GET 完成 ⇒ post-barrier 对本地可见性也不需要；
  • 每个 rank 必须设同一个 env，否则栅栏代际错位。

但默认不能关，因为栅栏代际是共享的（api.py:503 原话）： prefetch 的 host 栅栏与 planning/dispatch 的 device aclshmemx_barrier_all_vec 共用同一个 sync_counter；rank 间代际不一致就死锁。

已实测：全集群一起关（ASCEND_MOONEP_PREFETCH_RELAXED=1）⇒ 反而慢 2.9 ms ✗ —— 说明它们虽不保护数据，却在当前结构下承担 rank 对齐； 拿掉后偏斜不会消失，只是转移到后面的栅栏上。

栅栏收敛有两条路，可以叠加

路径做法栅栏数/层风险
B1把两个投影的 prefetch 合并成一个 kernel （内核改成一次收多投影、内部循环不同 Hp）4 → 2 低 —— 不动代际机制
B2把 prefetch 的同步从共享的栅栏代际里解耦 （改用独立 event / flag 轮询）2 → 0–1中 —— 要动同步设计

B1 是低垂果实：一次 launch 的成本 + 一对栅栏，每层都能省。

改造建议（详见 docs/design_moonep_bulk_transfer_and_sync.md）

  1. 大块化：put/get 次数 T×K → R−1（源端 compact + 接收端 permute）；
  2. B1 合并投影 prefetch：栅栏 4 → 2，低风险，可先行；
  3. B2 同步解耦：栅栏 2 → 0–1。不做这步，大块化的收益会被每层的栅栏等待吃掉一半。
