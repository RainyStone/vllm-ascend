两条路线:MC2(基线)vs MoonEP

MC2 —— 原生融合算子

  • npu_moe_distribute_dispatch_v2 / combine_v2,单算子完成交换 + GEMM 流水
  • MC2 = Matmul-Communication ×2;通信等待被 cube 覆盖
  • 底层 HCCL(all2all);无 plan 表、无跨层状态

MoonEP —— 对称内存单边

  • planning / dispatch / combine 三个 AscendC 核 + SHMEM RMA
  • 通信目标地址在 planning 阶段就完全确定(显式 plan 表)
  • 无握手协议,搬运可当纯数据搬移 —— 融合判断的关键
所有路线首 token 与 MC2 逐序列一致(=315);同窗口背靠背测量(本机跨窗口漂移 ±8%)。 owner 模式每卡 (token, expert) 条目 3175 vs 3155(差 0.63%),padding 149 条目/层。

4 卡示意:行怎么走(dispatch=PUT,combine=GET)

去重:同一 token 发往同一目标卡只搬一次,接收侧按 dup 表本地复制 ⇒ 网络搬运量按「不同目标卡数」计 (K=8/R=2 时约 4× 降幅)。

对称内存:是什么,里面装了什么

是什么:各 rank 在自己显存申请缓冲并把物理句柄注册给 SHMEM 运行时,运行时保证虚拟地址在每张卡上相同 ⇒ aclshmem_ptr(base, pe=r) 即可直接读写对端,不需要对方参与(单边)。

区域形状用途谁写
hidden_buf[NvS, H] bf16行缓冲:本卡收到的待算行 / 算完待取回的行对端 dispatch、本卡 combine prologue
weights_buf[NvS] fp32每行路由权重,与行同序搬运同上
barrier_buf / sync 区按 R 布局跨 rank 栅栏、combine grant/done、dispatch 每 token 同步各 rank
op workspace每核一段planning / combine 等核的临时区各核
planning inbox / flags按 R 布局各 rank 发布计数/前缀 + payload-done 旗标对端 planning 核
plan 表本身(dst / dup / cu_seqlens)在本地显存,不进对称内存 —— 对称内存只放"要被别人读写的通信数据"和"同步旗标"。

每段耗时(decode,每层每卡)

通信段合计 0.202 ms vs MC2 融合算子 0.157 ms(MC2 为 host 入队口径、异步,仅作参考)。 prefill 的 planning 核升到 0.26 ms —— 它是设备时间,随 N·K 行数线性。

①④⑦ 在干什么?是 SHMEM 的 overhead 吗?

步骤作用是 SHMEM overhead?能否省
① pad 0.035ms本步 T 行补到容量 C(零 hidden / 零权重 / 指向本卡首个专家) 部分是:静态容量来自"预注册对称缓冲";但 MC2 同样要 pad 到 padded_num_tokens real-T 路径(容量池已把平均补零降到 ~19 token)
① tpe 0.022ms统计每专家 token 数,喂给 planning 不是:显式 plan 方案的输入;MC2 在算子内自己算 能(挪进 planning 核),但只值 ~1%
④ 边界拷贝 0.018ms对称 chunk ↔ 调用方私有张量(两个方向) 是:共享 shard 会被对端/下一层覆盖,必须先拷出来 zero_copy 可省,但尾部 mask 成本 ≈ 拷贝 ⇒ 真解法是核只搬真实行
⑦ 加权把路由权重乘到 MLP 输出 不是:Ascend combine 核不支持前向加权(weights_buf 是训练反向的 gather);MC2 的 combine_v2 内部带权重 库侧支持 or 融进 GMM2 epilogue
⑦ 尾部清零where 清掉 sum(group_list) 之后的尾部 不是:combine 核按容量整块搬运的实现细节,不是 SHMEM 语义 核侧只搬真实行(它已拿到 group_list)
三步合计 ≈0.12 ms/层:真正由「对称内存 + 静态容量」强制的只有 pad + 边界拷贝 ≈0.053 ms; 其余 ≈0.066 ms 是库侧可改进项(直方图位置、combine 不支持加权、按容量搬运)。

planning 内部:有通信吗?表有什么用?

有 —— 它是跨 rank 协作核

  • 本地直方图(ReduceTpeRowsReg)
  • 发布计数/前缀到对端 inbox(PublishSourceDup*)
  • 等待payload-done 旗标(aclshmem_ptr(base, dest))
  • owner 端 reduce → 全局每专家负载
  • 落表 + 核尾全 rank 栅栏

通信量小(计数/前缀,不是 token),但同步面很宽 —— 必须在所有 rank 到齐后才有全局视图。

5 张表与收益

  • dst[N] → 静态寻址:接收偏移预定,无需原子分配/握手
  • dup_* → 去重:搬运量按"不同目标卡数"计(约 4× 降幅)
  • cu_seqlens → 直接当 group_list,无重排
  • experts_to_copy → 预取决策
  • zero_fill_ranges / stats → 省扫描 + 包络保护
结论:planning 是「全局耦合」阶段,dispatch/combine 是「点对点」阶段 —— 这决定了后面融合的边界画在哪。

prefetch 的位置,以及把它挪出关键路径

方案信号窗口正确性风险
(a) 精确版本层真实 plan与 dispatch / 边界拷贝 / 等对端行重叠 ≈0.05 ms无(改动最小)
(b) 预测版上一层 hidden(残差流)提前跑 gate整个 attention(decode 0.2~0.4 ms) 零:预测只决定预取哪些权重,真实路由照常
它顺手解掉融合的最大冲突:预取若在 attention 期间完成,融合核里这一步退化成"检查权重是否就位",不再产生核内等待。

预测不准怎么办?—— 不需要重新搬

情形会发生什么额外代价
命中(∈ 预测 ∩ 真实)权重已在本地槽,这些行本地算,GEMM 无等待—
未命中(∈ 真实 \ 预测)行按 owner 语义 dispatch 给属主卡(与今天默认行为一致)0 额外搬运(这条路径本来就要走)
预测多了(∈ 预测 \ 真实)白搬一趟权重,槽里副本没人用RMA 带宽 ≈9.4MB/专家/层 + 槽位占用

关键性质:预测只决定"哪些行留在本地算",不改变"行去哪算" ⇒ 最坏情况 = 今天的行为 + 少量白搬带宽,不会更差。

要避免的实现方式:写成"必须把 真实\预测 也补搬进本地才继续" ⇒ 补搬落回 GEMM 前,退回今天 prefetch 的亏法。

工程兜底

  • 只预取高置信度候选(top-1/2 或按门控得分阈值)
  • planning 后校验 |真实\预测| 与 |预测\真实|,差异超阈值就忽略预取成果
  • 小量补搬作为增强:塞进 planning/dispatch 窗口,而非 GEMM 前
  • 槽位淘汰策略;先测「相邻层 topk 重合率」决定值不值得做

什么是 Megas MoE(融合大算子)

把 MoE 一层里的多个阶段 —— token 交换、分组 GEMM、激活、加权归约 —— 收进同一个设备核, 用核内栅栏 / 多流水(cube 与 vector、搬运与计算)把通信等待藏到计算后面。业界三条路线:

MC2(本机基线)

dispatch/combine 与 GEMM 在算子内流水,是 Ascend 上现成的 mega-MoE 形态;通信底层绑定 HCCL。

fused-kernel 流派

DeepGEMM 风格:单核内完成分组 GEMM + 激活 + 归约,靠持久化线程块与流水隐藏搬运。

MoonEP 的对称内存流派

显式 plan + 单边 RMA,通信与计算目前是两个阶段(尚未流水) —— 这正是本报告要分析的融合对象。

融合的本质收益是让通信与计算重叠,其次才是省 launch 与中间张量往返。

推荐的融合边界

收益项估算(decode)说明
省 launch / 边界拷贝+3~5%6 个核 → 3 个核;省两份 32MB 级拷贝与中间往返
通信与计算重叠+5~10%dispatch PUT 与 GMM1 并行;combine GET 与 GMM2 重叠 —— MC2 目前领先的正是这部分
风险—要自写核内 GMM(放弃现成高性能库)是最大不确定性;planning 若进核会拖垮流水

结论与建议路径

  • 生态位判断:2 卡、E=128、均匀路由下 MC2 已接近最优;MoonEP 的结构优势(负载均衡、单边通信)要在 大 R / 跨节点 / 路由倾斜时才明显 —— 实测 0.63% 不均衡即实测"无可挖余量"。
  • 但融合这件事 MoonEP 占优:静态寻址 + 单边 PUT/GET + 无 HCCL 依赖,恰好是融合核需要的性质, 而 MC2 的融合算子是 vendor 闭源、无法改造。
  • 融合边界:核外 planning + 核内 dispatch/GMM1/激活/GMM2/combine;理论收益 decode +10~15%。
  • 落地顺序:
    1. 精确版 prefetch 重叠(无风险、改动小,先把重叠机制跑通);
    2. dispatch 与 GMM1 合核,验证通信隐藏的实际收益;
    3. 再评估自写 GMM 是否值得(收益最大、风险也最大);
    4. 预测版 prefetch 之前,先量「相邻层 topk 重合率」。
  • 库侧可直接提的改进:combine 只搬 sum(group_list) 行(顺带删掉尾部 mask)、 combine 支持前向加权(省掉外层加权)、直方图挪进 planning 核。
