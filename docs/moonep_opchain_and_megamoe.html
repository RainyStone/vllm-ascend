1. 背景:两条路线

① MC2 —— Ascend 原生融合路线(基线)

expert-parallel 的 token 交换由两个 aclnn 融合大算子完成: npu_moe_distribute_dispatch_v2 / combine_v2。 MC2 = Matmul-Communication ×2:dispatch/combine 与前后 GEMM 在算子内部流水, 通信等待被 cube 计算覆盖;底层是 HCCL(all2all)。对上层只暴露一次调用,没有 plan 表与跨层状态。

② MoonEP —— 对称内存单边路线(本研究)

token 行按「专家属主」经 CANN SHMEM 对称内存做单边搬运,替换 HCCL all2all。 与 MC2 最本质的区别:通信目标地址在 planning 阶段就完全确定(显式 plan 表), 因此收发双方不需要握手协议,搬运可以当作纯数据搬移来做——这也是后文判断"能否融进大算子"的关键。

2. 对称内存:是什么、里面装了什么

对称内存(SHMEM):每个 rank 在自己显存里申请一块缓冲,并把它的物理句柄 (Fabric V2 / shareable handle)注册给 SHMEM 运行时;运行时保证每张卡上这块缓冲的虚拟地址相同。 于是「rank r 的第 X 字节」可以用一个地址表达:aclshmem_ptr(base_va, pe=r), 任意卡都能直接读写,不需要对方参与 —— 这就是「单边(one-sided)」。 Ascend 上要求接收侧显式 aclrtMemSetAccess(我们在 DP 场景还修了它的逻辑/物理 device id 问题)。

3.1 第 ①④⑦ 步到底在干什么?是 SHMEM 带来的 overhead 吗?

这三步不含"通信/计算本体",最容易被看成纯开销。逐项拆:

步骤作用为什么需要是 SHMEM 的 overhead?能不能省
① pad
0.035 ms		 把本步 T 行补到容量 C:补的行 hidden 全零、路由权重为 0、专家指向本卡第一个专家 对称内存里的 hidden_buf 是 init 时一次性注册的固定形状 [NvS,H](NvS = C·K), planning/dispatch 核都按这个尺寸工作,所以每步必须凑满 部分是:静态容量是「对称内存 + 预注册缓冲」设计的直接结果;但 MC2 也要 pad 到 padded_num_tokens(HCCL 集合通信同样要求各 rank 对齐),所以"pad"本身不是 MoonEP 独有 走 real-T 路径:容量按步长池化(已做,把平均补零从 (S_max−T)·K 降到 ~19 token)或让核按真实 T 跑(未做)
① tpe
0.022 ms		 用 histc 统计每个专家的 token 数 planning 要先生成"全局每专家负载"才能算归属、去重、预取决策,而这份计数目前由 host 侧算好喂进核 不是:它是「显式 plan 表」方案的输入,而不是对称内存的要求。MC2 没有这步,因为它的负载统计在 vendor 算子内部完成 能:把直方图挪进 planning 核(核里本来就有 topk 数据)。收益仅 ~0.02 ms/层(≈1%),单独做不划算
④ 边界拷贝 ×2
0.018 ms		 dispatch 方向:对称 chunk 里的行/权重 → 调用方自己的张量;combine 方向:本卡 MLP 输出 → 写回对称 chunk 对称 hidden_buf 是所有层共用且会被对端写的;直接拿它去算 GEMM 会被下一层/对端覆盖, 所以先拷进私有张量 是:这是「单一共享对称缓冲 + 层间复用」的代价,但属于设计选择而非语义必然 能:zero_copy=True 直接吃 shard(尾巴必须清零,我们验证过 mask 方案正确)。但我们实测 mask 成本 ≈ 拷贝成本,打平 ⇒ 真正解法是让核只搬真实行(库侧改)
⑦ 加权
(含在 0.044 ms)		 把每行的路由权重乘到 MLP 输出上(combine 核只做 K 求和,不加权) Ascend 的 combine 核只在 output_sk 非空时使用 weights_buf,而那是训练反向的 权重 gather,不是前向加权 ⇒ 前向加权只能在外层做 不是:与对称内存无关,是「combine 核不支持前向加权」的能力缺口。MC2 的 combine_v2 内部就带权重 (expert_scales) 能:库侧让 combine 支持 weights,或把加权融进 GMM2 的 epilogue(融合核本来就该做这件事)
⑦ 尾部清零
(含在 0.044 ms)		 用 where(row_ids < sum(group_list)) 把行数之后的尾部清零 combine 核会读整块 [NvS,H](prologue 整块拷进对称 chunk),而 MLP 在 sum(group_list) 之后根本没写 ⇒ 不清零就会读到未初始化内存,静默算错 不是:是 combine 核「按容量搬运而不是按真实行数搬运」的实现细节,不是 SHMEM 语义 能:库侧让 prologue 只搬 sum(group_list) 行(它已经拿到 group_list)⇒ mask 可以直接删掉, 还顺带省掉尾部搬运带宽

小结:三步合计 ≈0.12 ms/层,其中真正由「对称内存 + 静态容量」强制的只有 pad(0.035)+ 边界拷贝(0.018)≈ 0.053 ms; 另外 ≈0.066 ms 来自「显式 plan 表把直方图留在 host」「combine 核不支持加权 / 按容量搬运」——这三条都是库侧可改进项, 不需要动 SHMEM 设计本身。其中"核按真实行搬运"与"combine 支持加权"值得作为对 ascend-moonep 的改进建议提出。

4. planning 内部:它有通信吗?产出的表有什么用?

4.1 有,而且是跨 rank 协作核

planning 不是纯本地计算。核内节奏(函数名取自 kernels/planning.cpp):

  • 本地直方图:各 rank 先算自己的 per-expert 计数(向量 reduce,ReduceTpeRowsReg 系列);
  • 跨 rank 汇总:把计数/归属行发布到对端对称内存的 inbox(PublishSourceDupCounts / PublishSourceDupPrefixes),对端 WaitForSourceDupInbox 等待, owner 端做 reduce 得到全局每专家负载;
  • 完成同步:用 payload-done 旗标(PublishSourceDupPayloadDoneFlags / WaitForSourceDupPayloadDoneFlags,写对端 aclshmem_ptr(base, dest) 的既定偏移)对齐各 rank;
  • 生成输出:BuildSourceDupDestinationPrefixes → MaterializeSourceDupOutputs 落表;核尾一次全 rank 栅栏。

也就是说:planning 的通信量很小(计数/前缀 + 旗标,不是 token 数据),但同步面很宽——它必须在所有 rank 都到齐后才有全局视图。这决定了后面融合判断:planning 是「全局耦合」的阶段,而 dispatch/combine 是「点对点」的阶段。

6. prefetch 在哪个阶段

prefetch 不在默认(owner)路径上,只在 MOONEP_SLOT_MODE=1(冗余专家平衡模式)里出现,位置是 dispatch 之后、专家 GEMM 之前: token_dispatch → prefetch_projections(plan.experts_to_copy) → grouped GEMM → token_combine。

  • 搬什么:被选中的「远程专家」的权重行(w13/w2),从对端对称权重区 GET 到本卡的 B 个槽 chunk;
  • 为什么:这些专家的 token 就不必发到对端了 —— 行留在本地,用槽里的权重本地算;
  • 代价:每层一次权重搬运(几 MB)+ 本地多算这些行 + 槽显存;所以只有在路由倾斜严重时才划算 (本机 2 卡 E=128 均匀路由下不均衡仅 0.63%,开着反而亏)。

6.1 把 prefetch 移出关键路径:提前预测 + 与 attention 并行

今天 prefetch 之所以"亏",本质是它又晚又在关键路径上:`experts_to_copy` 由本层 planning 产出, 而 planning 必须等本层 token 的 gate/topk 算完(门控依赖 attention 的输出)⇒ 预取只能插在 dispatch 之后、GEMM 之前,GEMM 要等它完成。破解办法就是给它找一个更早的窗口去跑:

方案用什么信号窗口正确性风险说明
(a) 精确版
(不提预测)		 本层真实 plan 的 experts_to_copy planning 之后 → GEMM 之前(可与 dispatch / 边界拷贝 / 等对端行重叠 ≈0.05 ms) 无 只把「预取」与「本层其余通信阶段」并行;窗口窄,但已能把 ~1 个专家的 9.4 MB (≈0.05 ms @200GB/s)藏掉。实现上只是把 prefetch 核挪到 dispatch 核之后异步发起
(b) 预测版
(你提的方案)		 上一层/本 block 输入的 hidden(残差流 hL-1)提前跑本层 gate, 得到预测 topk 整个 attention(decode 下 0.2~0.4 ms 量级,prefill 下更大) 零正确性风险(见右栏) 预测只决定"预取哪些权重";真实路由照常:预测命中 ⇒ 权重已在本地,这些专家可本地算或直接省掉一次等待; 预测不中 ⇒ 只是白搬了一批权重,结果不受影响(这也是它敢做预测的前提)

为什么这条路走得通

  • 信号够早:残差结构下 block 输入 hL−1 在上一层结束时就已可用(早于本层 attention), 而 attention 之后 h' = hL−1 + attn(…) 与 hL−1 高度相关 ⇒ 用它跑 gate 的 topk 有相当的重合度(需要实测:相邻层/topk 重合率)。
  • 机制已经现成:MoonEP 的 slot/prefetch 路径本来就是「plan → prefetch_projections → mte_get_nbi + aclshmem_quiet」,把驱动信号从"精确 plan"换成"预测 plan"即可, 不需要新硬件语义。
  • 解开融合的最大冲突:第 8 节列的冲突之一就是"prefetch 在 GEMM 前插入等待,破坏核内流水"。 一旦预取移到 attention 期间完成,融合核里这一步就退化成"检查权重是否已就位",不再产生等待。

限制与代价(必须一起说)

  • 只能提前搬权重,不能提前搬 token 行:行落到对端 shard 的偏移由精确 plan 决定, 而"发哪些行"还由发送方的 plan 决定 ⇒ 预测错的偏移会把数据写乱,因此 token 侧无法预测。 这条方案解决的是"权重搬运"这一半(prefetch),dispatch 的 token 搬运仍在关键路径上。
  • 预测准确率决定收益:命中率低时白搬的权重会占掉 RMA 带宽与槽位,反而拖慢真实流量。 建议只预取高置信度的少数候选(如 top-1/2 个远程专家)或按门控得分阈值裁剪。
  • 显存与槽位:预取要占 B 个槽 chunk;预测版可能同时保留"预测进来的"与"真实需要的"权重 ⇒ 需要槽位淘汰策略(或干脆只允许预测集合与真实集合取交集时复用)。
  • 实现位置:预测 gate 必须跑在 attention 之前 ⇒ 需要框架在 forward 里提供一个"提前 gate"的钩子 (vllm-ascend 已有 prefetch_mlp_gate_up_proj 之类的字段,可作为落点),与 MoonEP 库本身解耦。

预测不准会怎样?会不会把专家"重新搬一遍"?

不会。关键在于:预测只决定"哪些行留在本地算",而不改变"行去哪算"的基本规则。 真实路由出来之后,planning 照常生成计划,只是把预测命中(P ∩ T)的那部分专家算作"本地已就位", 其余专家(T \ P)的行仍然走今天默认就存在的 owner 路径——发给它们的属主卡去算。 也就是说,未命中时不需要补搬权重,那条路径本来就在跑,只是没能省下来而已。

情形会发生什么额外代价
命中(专家 ∈ 预测 ∩ 真实)权重已在本地槽,这些行本地算,GEMM 无等待—
未命中(专家 ∈ 真实 \ 预测)行按 owner 语义 dispatch 给属主卡(与今天的默认行为完全一致) 0 额外搬运(这条路径本来就要走)
预测多了(专家 ∈ 预测 \ 真实)权重白搬一趟,槽里的副本没人用 RMA 带宽 ≈9.4 MB/专家/层 + 槽位被占

所以最坏情况 = 今天的行为 + 少量白搬带宽,不会比现状更差;真正要避免的是把它实现成 "必须把 T \ P 也补搬进本地"(那会把补搬放回关键路径,退回今天 prefetch 的亏法)。

工程兜底(建议同时具备)

  • 只预取高置信度候选(top-1/2 个远程专家或按门控得分阈值裁剪),用命中率换带宽;
  • planning 后做一次校验:统计 |T \ P| 与 |P \ T|,差异超阈值就忽略预取成果(最坏退化为与今天持平);
  • 小量补搬作为可选增强:若 |T \ P| 很小(1~2 个专家),把它们塞进 planning/dispatch 那个窗口补搬(即前述"精确版"的窗口),而不是放到 GEMM 前;
  • 槽位淘汰策略:预测集与真实集并存时,优先保留将要使用的槽;
  • 可先测的第一个数据点:相邻层 topk 重合率(用同一份 prompt 跑一遍,统计 hL−1 与 h' 两套路由的 topk 重合度)——它直接决定预测版值不值得做。

结论:这是把 prefetch「从亏变赚」的正确方向 —— 预测版零正确性风险(预测只影响预取范围), 窗口大(整个 attention),而且顺手消掉融合核里最大的一个等待。它的上限是"把权重搬运完全隐藏", 即当前 slot 模式下每次 prefetch 的显存带宽与等待(≈0.05 ms/层/专家)可以不再计入关键路径; 代价是预测命中的工程质量与带宽竞争。建议的落地顺序:先做 (a) 精确版(无风险、改动小、验证重叠机制), 再评估 (b) 预测版需要的 gate 提前钩子与命中率。

7. 什么是 Megas MoE(融合大算子)

把 MoE 一层里的多个阶段 —— token 交换(dispatch)、分组 GEMM、激活、加权归约(combine) —— 收进 同一个设备核,用核内栅栏 / 多流水(cube 与 vector、搬运与计算)把通信等待藏到计算后面。业界三条路线:

  • MC2(本机基线):dispatch/combine 与 GEMM 在算子内流水,是 Ascend 上现成的 mega-MoE 形态;通信底层绑定 HCCL。
  • fused-kernel 流派(DeepGEMM 风格):单核内完成分组 GEMM + 激活 + 归约,靠持久化线程块与流水隐藏搬运。
  • MoonEP 的对称内存流派:显式 plan + 单边 RMA,通信与计算目前是两个阶段(尚未流水)。

融合的本质收益是让通信与计算重叠,其次才是省 launch 与中间张量往返。

8. 重点:把 MoonEP 融进 Megas MoE —— 亲和还是冲突?

逐维度对照 MoonEP 的设计与「单核多阶段流水」的需求:
