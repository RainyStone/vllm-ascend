定位证据
1. 旧实现：随机FP32系数在T=63、8191、8192出现错误，重复执行可能不同；固定1/K系数通过。
2. 只加S_MTE2：随机系数仍失败。该候选未被接受为修复。
3. 只把GetValue结果写入局部float变量、没有S_V：仍然失败。该负对照排除了“仅改变量写法便修好”的解释。
4. 局部float加S_V：原失败用例全部与独立CPU参考逐位一致，重复执行一致。
这将问题定位到动态路由系数的Scalar→Vector使用依赖。现有S_MTE2约束后续MTE2覆盖，不能代替S_V。当前反汇编工具未解码A5指令，具体VF融合/自动同步的指令级细节尚未证明，不将它写成已经确认的硬件细节。
本次没有改变BF16激活传输、FP32路由系数、FP32乘法与累加、最终一次BF16舍入。

有效修复（两个Muls位置分别处理acc和tmp）
    const float source_weight = source_weights.GetValue(
        src_route[i] - token_id * K);
    SetFlag<HardEvent::S_V>(EVENT_ID4);
    WaitFlag<HardEvent::S_V>(EVENT_ID4);
    Muls(acc_or_tmp, acc_or_tmp, source_weight, H);
源文件SCALAR_FENCE默认1。0和2仅保留用于负对照构建；失败的WEIGHT_REUSE_FENCE默认0。三个候选构建选项均为CMake可选诊断目标，未默认替换主库。

数值验证
A. S8192/H4096/K6，T=1、17、63、8191、8192：
   平衡、热点、远端热点流量；每路径3次随机系数重复、2次固定系数重复；旧发布/融合发布；两rank全部CPU参考不一致数为0。
B. S32768/H128/K6，T=1、17、63、65、1025、16385、32768：
   每个top-K专家使用不同的2的幂响应，避免恒等专家掩盖系数映射错误；每次使用新随机系数，每种T做3次；
   旧发布、融合发布、裁剪输入三路径，两rank共126次CPU逐位比较全部通过。
   T16385、32768覆盖每核512-token窗口切换；T65及以上覆盖输出缓冲区多次复用。
这些是小算子用例的验证结果，不表示模型精度或全部UDMA场景均已验证。

性能粗测
为使对照两端都正确，开销测量使用固定1/K路由系数。S8192/H4096/K6，T8192，双卡；
每种操作预执行5次，NPU events计时10次，交替操作顺序。
聚合：每次取两个rank耗时的最大值，再对10次取均值。
                              原库         S→V修复库
native weighted combine       4.695626 ms  4.661953 ms
旧发布+weighted combine       5.246383 ms  5.189572 ms
融合发布+weighted combine     5.061631 ms  5.020766 ms
native测量采用zero_copy=True、inter_rank_sync=False；内核自身的UDMA通信与同步仍在。
修复库native较原库为-0.72%，应按本次测量波动解释，未观察到明显额外开销，不宣称同步本身带来确定加速。
修复库内，融合发布相对旧发布耗时减少3.25%。
固定系数计时不构成原库随机系数正确性证据；也不能代替LongBench服务性能测试。
