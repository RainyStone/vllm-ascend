01核心结论

16K / 8K 的回退来自“到达时序触发错位 + 异步调度维持错位 + 跨 rank 并行度下降”的组合。 slot 对热点专家的均衡收益一直存在；当真实请求与 dummy 长期交错，更多全局轮次需要承担大 token 模型计算和通信，额外成本超过 GMM 节省，端到端便慢于 off。

① 分词分批释放请求默认 2ms 聚合窗口把首批 16 个请求切成 1+15；后 15 个约晚 437ms 就绪。
本工作负载的触发因素。
② 首批准入差两轮先到请求启动 DP wave，空 rank 先提交 dummy；后来请求不能替换已提交轮次。
slot 常见初始偏移 [0,2,2,2]。
③ 三轮节拍锁住错位9GiB KV 与异步输出回收形成 P1、P2、D；2 mod 3 ≠ 0，混合轮持续出现。
切分改变了相位能否自然重合。

高倾斜度下，只要跨 rank 真实工作集中在同一批轮次，slot 把热点专家的有效路由行分配给更多计算 rank，降低最慢 rank 的 GMM 工作量。这能补偿规划、权重预取及通信的成本。历史 8K/8K、8K/16K、16K/16K 的收益，与修复后 16K/8K 的收益符合这一机制。

高倾斜收益与切分回退，为什么能同时成立？

off 的专家计算仍主要受热点 owner rank 限制；slot 借助额外 expert slot 与权重预取，让其它 rank 承担热点专家的真实路由行。倾斜越高，消除热点 GMM 长尾的收益通常越大；倾斜低时，额外通信、预取和容量操作可能无法被摊薄。历史 uniform 的四种组合均无收益，说明 slot 不是所有负载下都应启用。

16K 不切分的实测稳态为 P→D，两轮初始偏移是完整周期；16K 切两块后为 P1→P2→D，相同两轮偏移不再是完整周期。于是单纯缩小 token 预算，除了增加分块，还改变了各 rank 真实计算能否同轮发生。

两个独立 8K 请求也不等同于一条 16K 请求的两个 chunk。后者有同一请求的 KV 生命周期、P1→P2 依赖、较长的第二块上下文，以及最后一块完成后才回收整条请求 KV 的约束；独立 8K 请求有各自的准入与完成边界。8K 历史收益不能直接套成“16K 切两次必然等于 2×8K”，也不能由此断言每个 8K 算子变慢。

03分词如何影响真正送入模型的 batch

HTTP 请求 → 分词微批 → token IDs 就绪 → DP rank 选择 → 引擎 WAITING → schedule() → 本轮模型 batch

调度器只能挑选已经完成前端预处理、且已被本 rank 引擎处理的请求。HTTP 同时到达不等于四个引擎同时拥有可调度请求。旧版 AsyncMicrobatchTokenizer 会先在前端聚合文本，批量分词完成后再释放结果；后续请求仍以独立请求进入引擎。

04固定错位是怎样形成并持续的

第一步：空 rank 已提交的 dummy 不能由迟到请求替换

首请求被分给一个 rank 后，FIRST_REQ / START_DP_WAVE 让其它 rank 进入共同执行波次。没有真实请求的 rank 必须参与 DP/EP 集合通信，于是执行 dummy。引擎在外层循环处理新输入；当 dummy 调用已提交且尚未返回时，后来的请求只能等待后续调度轮。

slot 的一个直接实测样本中，rank1/2/3 在约 2ms 提交第一轮 dummy，在约 115ms 提交第二轮；它们的真实请求约 418–421ms 才被前端选中分发，约 1.25s 才进入第一轮真实 forward。因此初始真实 forward 偏移为 [0,2,2,2]。不同运行中的具体毫秒值会变，先提交两轮 dummy 的因果顺序不变。

第二步：KV 回收顺序制造每请求后的空轮

  1. 16K 请求 A 的 P1、P2 分别调度 8192 token；最后一块在途时，A 仍占用 KV。
  2. step_with_batch_queue() 优先尝试 schedule / submit，然后消费旧输出。A 已知将达到 max_tokens=1，不再需要额外调度；WAITING 中请求 B 却因剩余 KV 不足而被拒绝。
  3. 这一轮 schedule 得到 0 token；随后消费 A 的最后输出，A 完成，KV 被释放。
  4. 该分支没有在回收后重新调度，model_executed=False 仍保留。波次尚未结束，DP 引擎执行一轮 dummy。
  5. 下一次循环 B 才可获得 KV，形成 P1 → P2 → D 的稳定节拍。

D 是调度 bookkeeping 空轮转成的 dummy，不是请求额外生成一个业务 token 的 decode。本样本在 KV 拒绝时剩余 4335 blocks；下一块自身就需要 6722 blocks，完整 16K 请求占用 13444 / 17779 blocks。即使关闭 full-sequence-fit 检查，也不保证消除空轮。block 计数不是 token 数。

初次实机两腿共 54 次“有等待请求但空调度”均核对了 KV 拒绝 → 空调度 → KV 释放 → executed=False → dummy → 下一次真实调度 链条。这一节拍由本次 KV 容量、输出长度和异步队列共同形成，不是 vLLM 任意配置必然每三轮插一次 dummy。

两种三轮周期处理的真实 chunk 总量相同，区别在于真实工作是否并行集中。错位让各 rank 的 attention、共享专家等本地计算分散在更多全局轮次，跨 rank MoE 通信又要求保持同一 collective 次序。因此 token 总量相同，也会增加端到端关键路径时间。

证据：逐请求 KV / dummy 因果链与源码行号，同服务自然对齐样本。

05为什么 slot 高频错位，off 常规运行却较少表现出来

off 没有额外的“请求阶段自动对齐保证”。两种模式都可能有 dummy，也都受同一前端分词就绪差影响。差别在于 worker 提交、同步与背压的实际耗时不同，迟到请求赶上了不同的轮次边界。

自然对齐那一次，究竟触发了什么？

同一个 slot 服务的自然对齐组，前四次 frontend_dispatch 相对首请求仅差 [0,0.912,1.637,2.281]ms，四个 rank 都及时拿到真实请求；下一簇 12 个请求约在 352ms 后。TTFT 从前一错位组 13.1971s 降为 9.2800s，稳态周期从 3.9816s 降为 2.8355s。

06slot 多出的约 2.54 秒，实际花在哪里

历史 clean 样本差为 2.5438s；后续同卡组轻量 profile 的客户端差为 2.5062s。以下分账精确对应后者，不能把不同运行的数字硬拼成历史 2.5438s。采样条件为 NPU-only / Level1，无 CPU capture、stack、memory 或 AIC metrics。

计算口径：每层取四 rank 对应阶段的最晚完成边界，组成不重叠的全局时间区间；每个区间乘以当时未完成请求数 / 32，得到对平均服务端 TTFT 的贡献。每个时间区间只记一次，不把各 rank 等待相加，也不把算子时长总和当成客户端延迟。

如何读这个分账

  • GMM 已经获益：slot 节省约 2.167s。不能说“slot 均衡算法把专家 GMM 算得更慢”。
  • 主要不利项：dispatch/combine 多约 1.981s，combine 前容量张量处理多约 0.930s，其它模型计算与轮次间隔多约 1.747s。错位把真实工作分散到更多串行全局轮次，是这些成本暴露更多的关键原因。
  • planning 不是秒级主因：四 rank 原始 planning 时长相加约 30.243s，但最后 rank 到齐后的全局规划区间累计约 0.0895s；对平均请求的关键路径贡献只有 0.0268s。长 planning 等待说明某些 rank 提前到集合点，不能再把同一时间其它 rank 的计算重复计费。
  • 预取是次要项：约 0.254s 的暴露成本，值得优化，但不能解释整个差额。

combine 准备中实际 device 工作主要为 Mul 0.377s、Cast 0.363s、SelectV2 0.229s、TensorMove 0.235s，说明这里有真实的整容量读写。其它模型项包括 attention、投影、norm、HC、共享专家、router 与少量轮次边界，不等于全是 CPU 空转。

同形状、同 P1/P2 的 attention 对比中，slot 均值约 3.349 / 3.718ms，off 约 3.421 / 3.829ms。没有证据表明 slot 把同一个 attention kernel 拖慢；总关键路径贡献增加主要与真实工作分散到更多轮次有关。这里也没有通过消融证明 polling 资源竞争的独立份额。

对早期判断的更新：“planning 等待总量增长”是错位的症状，不能直接当成根因或全部性能差额。只缓存 plan、减少 barrier 次数，并不能据此保证消除本次回退；先修复准入时序并验证相位，证据更直接。

数据：关键路径阶段 CSV · 采样边界核算与 clean 对照。off 在连续运行中曾伴随温度/频率变化变慢；最终收益另用同样冷却条件的三组配对，不由本 profile 表外推。

07slot 均衡的是哪些 token？off 有 dummy 为什么仍较快？

需要区分三个量：业务真实 token、dummy forward 自身的 1 个输入 token、为容量 / 通信对齐预留的 padding。本次 slot 启用 MOONEP_REAL_T=1；T 是本地有效输入行数，S 是容量档位，K=6。

环节slot：本次 real-T 路径off：本次大 token / mixed 路径
参与路由 / 均衡的输入按真实 T 构建直方图；dummy 本身 T=1，也有 6 条有效 route；S−T 尾部不进入有效负载实际走 DP ALLGATHER：先 pad 到跨 rank 最大 T，再 allgather；本模拟路由在 MoE 前不 unpad
GMM按 owned + slot 的实际 group_list 有效行数计算；可接收其它 rank 的真实 tokenmixed padding 在本模拟路由下也会进入专家路由 / GMM
容量操作NO_SYNC 保留 S×K 的容量张量，copy、量化、激活、乘权、转换、where 清尾、搬运仍可能处理尾部mixed 轮负担大；全 dummy 时实际切换为便宜 MC2 路径
dummy rank 有大 GMM 是否代表算 padding？不一定：它可作为 owner 或 slot 承担来自其它 rank 的真实专家计算owner rank 也可能承担其它 rank 的真实请求计算
混合轮：本地有效 T = [8192, 1, 1, 1]，K = 6
slot 有效路由行总量 = (8192 + 1 + 1 + 1) × 6 = 49,170
不是按全容量计算的 4 × 8192 × 6 = 196,608

slot 理想 fair-share 基准 = floor(49,170 / 4) = 12,292 行
实际分配还受专家 / slot 约束，不保证精确等分。
单 rank 容量 NvS = 8192 × 6 = 49,152，hidden size H = 4096。

因此，本次 slot 并没有把 8K 容量尾部全部当作“有效专家负载”去均衡；但 padding 的逐元素 / 内存成本仍在。旧 MOONEP_REAL_T=0 路径可能把 padding 带入有效路由，不能与本次路径混为一谈。

对 off，trace 在 [8192,1,1,1] mixed 轮看到 MoeInitRoutingV3 输入 32768×4096 / 32768×6，GMM 容量 196608 行；其代价接近全真实轮。全 dummy 轮则只有 24 行 GMM 输入，profile 中每层 MoE 约 0.541ms，其它模型部分约 1.074ms，便宜得多。

关键不是 dummy 的总个数，而是它们是否聚集在同一全局轮。通常 off 的稳态为两轮全真实 + 一轮全 dummy；错位 slot 每轮都有真实 8K 工作。off 可拥有更多 dummy forward 却更快；若人为让 off 也长期 mixed，它同样退化。

以上 backend、padding 和 GMM 行为限于本次 TP1 / DP4、模型、路由和代码版本。不能泛称所有 off 场景都使用 ALLGATHER，或所有 padding 都会进入 GMM。

统计口径：前 3 组和后 4 组分别取算术均值；输入吞吐先按每组 total_input_tokens / duration 计算再平均。它们使用不同 seed，属于同服务的窗口切换重复验证，不能称为同 seed 的逐组配对。baseline3 的实验包装中断，沿用原有效性筛选，使用完整的 baseline3_retry。3 组默认窗口中，baseline2 的偏移为 [0,0,2,2]，其余为 [0,2,2,2]；均产生 18 个混合轮。

“修复后”的含义：该组在运行中的分词实例上把已有窗口改为 20ms，用于确认方案的因果效果；交付的 patch 把这个窗口暴露为环境变量。通过环境变量启动的新 slot 服务已另外重复验证：主三组平均 TTFT 9.4755s，与这里的 9.4706s 接近。这不是重新采集的新实验。

跨模式精度限制需要保留：仿真路由 moe_sim_route._assign 使用 randperm(T) 生成专家表。slot 真实 T=8192，off ALLGATHER 后 T=32768；同 seed 和同分布不保证同一业务 token 选中相同专家。执行原始路由函数的 CPU 验证中，每 rank 8192 行的完整 6 专家选择仅 18 / 27 / 35 / 30 行跨模式一致。因此这组仿真输出不能作为跨模式数值等价 oracle；该差异在窗口补丁前已存在，同时也不能排除其它数值差异。

要验证真实模型质量或 slot/off 数值等价，下一步应使用真实路由，或把模拟路由固定到全局 token 身份，使两模式逐 token 专家选择一致，再进行多请求、多输出长度的逐 token / logit 对照。本报告没有把性能验证代替模型质量验证。

  • 每卡保留 16GiB 的占位进程覆盖服务切换，并采样进程、温度与频率；这不是驱动级排他锁。
  • 最终 slot 第二次启动首次外来进程告警为 22:16:21；主三组性能样本均在 22:13:36 前结束，且有前后无告警采样。告警后第 4 对只作为补充，不纳入主均值。
